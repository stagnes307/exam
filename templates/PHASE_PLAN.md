# Phase 개발 계획과 실행 근거

AI 개발용 상세 양식이다. 2단계에서 실제 정한 Phase만 `plans/P1.md` 같은 파일로 작성한다. 현재 필요한 절만 사용하고 미래 기능·빈 실행 표를 미리 늘리지 않는다. 사용자가 읽을 설명·직접 테스트·인지 대비 정보는 `PROGRESS.md`에 작성한다.

## 범위와 선행 조건

| Phase ID·상태 | 관련 요구·PRD/PLAN 링크 | 선행 Phase/조건 | 실행 가능한 결과·완료 기준 |
| --- | --- | --- | --- |
| | | | |

- 승인된 범위·사용자 요청 근거:
- `PLAN.md`의 관련 질문/변경 ID·확정 해석 링크·미확정 의존 범위:
- 이번에 포함하지 않는 후속 통합 범위:

담당자 답변 원문은 `PLAN.md`만 참조한다. 사용자에게 PRD·기술 계획 전체를 읽었다고 말하게 하지 않고 `PROGRESS.md`의 범위/선택 사항을 확인한 실제 요청을 근거로 삼는다.

## 구현 작업

| 작업 ID·요구 ID | 구현할 기능·파일/함수 | 선행 작업 | 완료 기준·검증 ID | 상태·다음 작업 |
| --- | --- | --- | --- | --- |
| | | | | 미구현·미실행 |

Phase 안의 연결된 여러 기능·수정·재검증은 이어간다. 기능마다 재승인받지 않는다. 아직 없는 DB·UI·배포를 검사 표를 채우려고 추가하지 않는다.

## 검증 계획과 실제 결과

기대값은 앱 출력 전에 원문·손계산 등 별도 근거로 정한다. 실행 전 계획과 실제 수행 결과를 구분하고, 미실행·실패·현재 판본에서 재확인 필요를 그대로 표시한다.

| 검증 ID·요구 ID | 초기 상태·입력/조작 | 기대·원문/독립 계산 근거 | 명령·작업 디렉터리·판본 | 실제·종료 코드·확인 주체·미확인 |
| --- | --- | --- | --- | --- |
| | | | | 미실행 |

- 공유 파서/계산/시간 함수가 함께 틀릴 수 있는 사례와 독립 대조:
- 생성기 재실행과의 일치 대신 입력·최종 출력 제약을 직접 검사한 근거:
- 다른 유효 결과 수용·정상 결과 복사본의 고의 오류 거절:
- 단일 건/하루와 전체 기간·공유 자원 검사 구분:
- 미배정/거절 사유·누적 제약의 기준 시점과 우선순위 대조:
- 실패 원인·수정 위치·같은 사례/기존 정상 흐름의 재검증:

원본 자료와 정상 결과는 보존하고 변경/고의 오류 검사는 복사본으로 한다. 기술 결과를 AI 확인·사용자 직접 확인·설명 제공·사용자 이해·실제 제출과 구분한다.

### 데이터 적용부터 출력까지의 일관성

실제 데이터 변경·생성·저장 요구가 있을 때 적용한다. 정상 A·오류 B·변경 C는 복사본으로 준비하고 자료 종류별 변경도 확인한다. 없는 기능은 후속 통합 검증으로 연결하고 해당 없는 조건은 이유를 적는다.

| 시나리오 | 확인할 관계·상태 | 입력/조건/결과 식별 근거·검증 ID·실제/미확인 |
| --- | --- | --- |
| 정상 A 적용·생성 | 선택/검증/적용 데이터와 생성 조건·결과가 대응 | |
| 오류 B 적용 거절 | 오류 원인 표시, 기존 A·확정 결과 유지 | |
| 정상 C 적용 | 과거 결과가 C의 최신 결과처럼 표시/내보내기되지 않음 | |
| C 재계산·저장·조회·내보내기 | 검사한 결과와 저장/조회/출력의 데이터 판본·조건·내용 일치 | |
| 처리 중단·검증 실패·재시작 | 부분 결과를 완료로 공개하지 않음, 기존 결과·복구 상태는 요구대로 유지 | |

식별 근거는 실제 ID·조건·해시·레코드 등으로 남기며 특정 버전 관리 구현을 강제하지 않는다. 건수나 출력 변화 여부만으로 재계산·내용 일치를 증명하지 않는다. 여러 Phase에 걸친 시나리오는 `PLAN.md`의 담당 Phase에서 최종 증거를 관리한다.

### 품질과 비용 비교

| 입력/조건·규모 | 기준 방법·현재 방법 | 규칙 준수 | 품질 지표·실제 값 | 실행 비용·차이·한계·검증 ID |
| --- | --- | --- | --- | --- |
| | | 미확인 | | |

같은 입력으로 비교한다. 지표의 정의·방향·선택 이유는 PRD를 연결하고 실행 시간 등 측정한 비용을 적는다. 규모 확대와 핵심 조건 변경도 확인한다. 개선되지 않은 지표·손실·미실행을 공개하고 임의의 개선률을 만들지 않는다.

## 코드 책임과 실패 상태

구현할 때부터 실제 코드로 기록한다. 기능별 입력 예시·파일/함수·선택 이유·한계와 재현 근거를 아래 표에 연결하고, 쉬운 설명은 `PROGRESS.md`에 요약한다.

| 규칙·요구 ID | 직접 검사 / 다른 계층 위임 / 미구현 | 담당 코드/계층·보장 범위 | 재현 명령·증거·한계 |
| --- | --- | --- | --- |
| | | | |

| 실제 상태 | 담당 컴포넌트·보관 위치 | 확정/갱신 시점 | 실패·중단 후 남는 것·복구·확인 근거 |
| --- | --- | --- | --- |
| | | | |

진행 중 작업·임시 결과·최종 결과를 실제로 존재하는 만큼 구분한다. 없는 상태·Worker·큐·별도 프로세스는 가정하지 않는다.

## 변경·재확인과 Phase 종료

| 판본·변경 ID | 변경 내용·이유/근거 | 영향받는 요구·Phase·검증 | 수정/재검증·재확인 필요 |
| --- | --- | --- | --- |
| | | | |

- 사용자 확인: `PROGRESS.md`의 보고 주체·판본·범위/결과 링크:
- 필수 제출물·지정 문서에 반영한 근거·실제 경로:
- 현재 구현/AI 검증/미구현/실패/미확인·남은 통합 검증·다음 작업:
- 중간 종료 시 진행 중/부분/확정 결과·미저장 변경·현재 제출 준비 상태:

현재 상태를 먼저 갱신하고 과거 검증은 판본과 함께 짧은 이력으로 남긴다. 계획 전체·프롬프트·사용자 보고를 매번 복사하지 않는다. 코드·자료·조건 변경이 과거 정상 항목에 영향을 주면 검증과 사용자 확인을 재확인 필요로 표시한다. 요구·완료 기준·다른 Phase 범위/순서가 바뀌면 PRD와 `PLAN.md` 목차·관련 Phase도 갱신한다. Phase 결과·직접 테스트 안내·인지 대비 설명·다음 PROMPTS 절 안내는 `PROGRESS.md`에 반영하고 사용자 요청을 기다린다.
