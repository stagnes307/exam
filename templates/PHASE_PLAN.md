# Phase 개발 계획과 실행 근거

AI 개발용 상세 양식이다. 2단계에서 실제 정한 Phase만 `plans/P1.md` 같은 파일로 작성한다. 현재 필요한 절만 사용하고 미래 기능·빈 실행 표를 미리 늘리지 않는다. 사용자가 읽을 설명·직접 테스트·인지 대비 정보는 `PROGRESS.md`에 작성한다.

## 검증 계획과 실제 결과

기대값은 앱 출력 전에 원문·손계산 등 별도 근거로 정한다. 실행 전 계획과 실제 수행 결과를 구분하고, 미실행·실패·현재 판본에서 재확인 필요를 그대로 표시한다. 구현된 CLI/API·입력 검증·자동 회귀 검사와 실제 UI가 있을 때의 기능 검사는 AI가 직접 수행하고 실패를 수정·재검증한다. 이미 통과한 같은 명령을 사용자가 다시 실행하는 것을 Phase 종료 조건으로 삼지 않는다. 필수 검사 중 실행하지 못한 항목은 원인·범위·영향을 미확인으로 남기고 검사 성공이나 완료를 지어내지 않는다.

| 검증 ID·요구 ID·검사 계층 | 계획 수행 주체·담당 Phase·실행 시점/선행 조건 | 초기 상태·입력/조작 | 기대·원문/독립 계산 근거 | 명령·작업 디렉터리·판본 | 실제·종료 코드·확인 주체·미확인 이유 |
| --- | --- | --- | --- | --- | --- |
| | | | | | 미실행 |

검사 전 각 필수 검사의 수행 주체·시점·선행 조건·완료 기준과 근거 위치를 계획한다. 모듈/CLI/API·UI 기능·전체 연결 흐름을 구분하고, 단위검사 통과만으로 UI나 전체 흐름 통과를 기록하지 않는다. 없는 후속 기능의 통합 검증은 `PLAN.md`의 담당 Phase와 실행 조건으로 연결한다. 현재 Phase 필수 검사에 실패·미실행이 남으면 해당 검증은 미완료이며, 현재 완료 기준 충족과 후속 통합 미완료는 별도로 표시한다. 매 Phase에 전체 미래 기능 검사를 강제하지 않는다.

- 공유 파서/계산/시간 함수가 함께 틀릴 수 있는 사례와 독립 대조:
- 생성기 재실행과의 일치 대신 입력·최종 출력 제약을 직접 검사한 근거:
- 다른 유효 결과 수용·정상 결과 복사본의 고의 오류 거절:
- 단일 건/하루와 전체 기간·공유 자원 검사 구분:
- 미배정/거절 사유·누적 제약의 기준 시점과 우선순위 대조:
- 실패 원인·수정 위치·같은 사례/기존 정상 흐름의 재검증:

원본 자료와 정상 결과는 보존하고 변경/고의 오류 검사는 복사본으로 한다. 영구 데이터셋은 원문이 요구한 준비 자료와 실제 선택·재현에 필요한 묶음으로 제한하고 목적을 기록한다. 세부 경계값·조합별 테스트 복사본은 임시 디렉터리에서 생성·정리한다. 원문이 요구한 정상/오류 준비 자료는 실제 파일로 보존하며 임시 테스트만으로 대체하지 않는다. 이미 검증 명령·문서에서 사용하는 자료는 영향 확인 없이 삭제하거나 합치지 않는다. 기술 결과를 AI 확인·사용자 직접 확인·설명 제공·사용자 이해·실제 제출과 구분한다.

### 데이터 적용부터 출력까지의 일관성

실제 데이터 변경·생성·저장 요구가 있을 때 적용한다. 정상 A·오류 B·변경 C는 복사본으로 준비하고 자료 종류별 변경도 확인한다. 없는 기능은 후속 통합 검증으로 연결하고 해당 없는 조건은 이유를 적는다.

| 시나리오 | 확인할 관계·상태 | 입력/조건/결과 식별 근거·검증 ID·실제/미확인 |
| --- | --- | --- |
| 정상 A 적용·생성 | 선택/검증/적용 데이터와 생성 조건·결과가 대응 | |
| 오류 B 적용 거절 | 오류 원인 표시, 기존 A·확정 결과 유지 | |
| 정상 C 적용 | 과거 결과가 C의 최신 결과처럼 표시/내보내기되지 않음 | |
| C 재계산·저장·조회·내보내기 | 검사한 결과와 저장/조회/출력의 데이터 판본·조건·내용 일치 | |
| 처리 중단·검증 실패·재시작 | 부분 결과를 완료로 공개하지 않음, 기존 결과·복구 상태는 요구대로 유지 | |

식별 근거는 실제 ID·조건·해시·레코드 등으로 남기며 특정 버전 관리 구현을 강제하지 않는다. 건수나 출력 변화 여부만으로 재계산·내용 일치를 증명하지 않는다. 여러 Phase에 걸친 시나리오는 `PLAN.md`의 담당 Phase에서 최종 증거를 관리한다.

같은 입력으로 비교한다. 지표의 정의·방향·선택 이유는 PRD를 연결하고 실행 시간 등 측정한 비용을 적는다. 규모 확대와 핵심 조건 변경도 확인한다. 개선되지 않은 지표·손실·미실행을 공개하고 임의의 개선률을 만들지 않는다.

### 알고리즘 정확성·요구 수준 확인 — 해당 과제만

알고리즘을 구현하는 담당 Phase의 기존 검증 표에 필요한 근거를 연결한다. 다른 Phase나 해당 없는 과제에 아래 방법을 모두 반복해서 강제하지 않는다.

- **정의와 구현 대조:** 원문의 입력/출력·유효 범위·선행 조건·제약·목표·우선순위·요구한 정확성/최적성을 실제 상태·변수·조건·결과 계산과 대조한다. 정의를 구현 편의에 맞춰 바꾸지 않는다.
- **선택과 정확성 설명:** 입력 규모와 전제에 맞는 알고리즘을 고르고 왜 올바른지 설명한다. 불변식, DP 상태의 충분성과 전이의 완전성, 탐욕 선택의 교환 논증, 후보 탐색의 누락 없음, 유효한 해결기 증명 등 선택한 접근에 필요한 근거만 사용한다. 근거 없는 형식 증명이나 모든 기법의 나열로 대신하지 않는다.
- **독립 작은 참조 검사:** 원문 정의로부터 작은 전수검사·단순 참조 구현 등 독립 기준으로 정상·경계·반례·무작위 소규모 사례를 비교한다. 생성기 재실행·자체 보고 점수만으로 검사하지 않는다. 제약과 점수/목적값을 독립 계산하고 다른 유효 결과도 수용한다. 정확해 요구는 최적값 일치를, 허용된 근사/휴리스틱은 필수 제약·점수·우선순위와 품질 격차를 검사한다. 후자의 최적값 차이 자체를 오류로 삼거나 임의 합격 임계값을 만들지 않는다.
- **실패의 회귀 검증:** 차이가 발견되면 실패를 재현할 작은 반례로 줄여 원인을 수정하고 회귀 검사로 보존한다. 작은 검사 통과는 그 범위의 증거이며 모든 입력의 정확성 증명으로 확대하지 않는다.

질문·답변의 해석으로 정한 사례는 PLAN의 AI 검토를 연결한다. 구현 중 그 해석과 다른 결과가 나오거나 목표만 유리해지는 편법이 의심되면 원문/자료와 구현을 먼저 대조하고, 업무 모호함이 남을 때만 후속 질문한다. 답변이 바뀌면 영향받은 작업·검사를 재확인하고 원래 기록은 보존한다.
- **규모와 기준 비교:** 큰 입력의 시간·공간 조건을 분석하고 필요한 실측·한계를 기록한다. 같은 정의·제약·목표/우선순위의 유효한 기준 방법과 비교하되, 더 나은 점수나 기준 대비 개선을 최적성 증명으로 쓰지 않는다. 열세·허용된 절충·미실행도 공개한다.
- **주장의 수준:** 정확한 방법·근사 보장·휴리스틱을 구분하고 실제 구현의 제한을 밝힌다. 최적성은 적용 가능한 정확성 근거·증명이나 실제 해결기 상태·유효한 한계값/차이로 뒷받침할 때만 주장한다. 알려지지 않은 상태·한계값·차이 0을 지어내지 않으며 해결기의 상태가 원문 모형과 구현의 정확성을 자동 보장한다고 쓰지 않는다.

검사 자료는 원문에서 도출해 가능한 한 임시 복사본으로 재현하고 필요한 반례의 재현 방법은 회귀 검사에 남긴다. 특정 업무 상수·정답 배열을 운영 입력에 하드코딩하지 않는다. 과제가 요구한 준비 자료는 보존하며 특정 해결기·새 패키지·별도 Phase를 필수로 추가하지 않는다.

## 코드 책임과 실패 상태

구현할 때부터 실제 코드로 기록한다. 기능별 입력 예시·파일/함수·선택 이유·한계와 재현 근거를 아래 표에 연결하고, 쉬운 설명은 `PROGRESS.md`에 요약한다.

| 규칙·요구 ID | 직접 검사 / 다른 계층 위임 / 미구현 | 담당 코드/계층·보장 범위 | 재현 명령·증거·한계 |
| --- | --- | --- | --- |
| | | | |

| 실제 상태 | 담당 컴포넌트·보관 위치 | 확정/갱신 시점 | 실패·중단 후 남는 것·복구·확인 근거 |
| --- | --- | --- | --- |
| | | | |

진행 중 작업·임시 결과·최종 결과를 실제로 존재하는 만큼 구분한다. 없는 상태·Worker·큐·별도 프로세스는 가정하지 않는다.

## 변경·재확인과 Phase 종료

| 판본·변경 ID | 변경 내용·이유/근거 | 영향받는 요구·Phase·검증 | 수정/재검증·재확인 필요 |
| --- | --- | --- | --- |
| | | | |

- 사용자 직접 확인 필요 여부·이유 / AI가 실행할 수 없는 필수 검사라면 실행 시도·환경 해결 검토·남은 최소 범위 / 필요한 경우 `PROGRESS.md`의 실제 보고 주체·판본·범위/결과 링크:
- 필수 제출물·지정 문서에 반영한 근거·실제 경로:
- 현재 구현/AI 검증/미구현/실패/미확인·남은 통합 검증·다음 작업:
- 중간 종료 시 진행 중/부분/확정 결과·미저장 변경·현재 제출 준비 상태:

현재 상태를 먼저 갱신하고 과거 검증은 판본과 함께 짧은 이력으로 남긴다. 계획 전체·프롬프트·사용자 보고를 매번 복사하지 않는다. 코드·자료·조건 변경이 과거 정상 항목에 영향을 주면 검증과 사용자 확인을 재확인 필요로 표시한다. 요구·완료 기준·다른 Phase 범위/순서가 바뀌면 PRD와 `PLAN.md` 목차·관련 Phase도 갱신한다. Phase 결과·인지 대비 설명·미확인은 `PROGRESS.md`에 반영한다. CLI만 있는 Phase의 AI 검증을 마쳤다면 요약·한계를 확인하도록 하고 다음 Phase의 3번 요청을 안내한다. 조작성·업무 수용 판단에 사람이 필요하거나 사용자가 직접 시험을 요청한 경우, 또는 필수 검사를 AI가 실제 환경에서 실행하려고 시도하고 해결을 검토했지만 수행할 수 없어 최소한의 사용자 확인이 필요한 경우에만 이유·범위와 결과 전달용 4번을 안내한다. AI 수행 불가를 검사 통과로 바꾸거나 전체 검사를 사용자에게 전가하지 않는다. 실제 대상 Phase와 할 일을 먼저 쓰고 사용자 요청을 기다리며 다음 Phase를 자동으로 시작하지 않는다.
