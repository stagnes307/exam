# 실제 구현 설명

사용자가 5단계 설명을 요청했을 때 현재까지의 코드를 근거로 작성한다. 전체 구현·사용자 테스트 완료를 전제로 하지 않는다. 계획의 기능별 짧은 설명과 책임표를 참조하고 지정 실행·설명 문서가 같은 역할을 맡으면 거기에 반영한다.

## 기준과 확인 범위

- 문서 상태: 초안 / 사용자 확인 범위 반영
- 기준 코드 판본·입력/조건·현재 Phase:
- PRD·계획·사용자 테스트의 실제 경로:
- 사용자 요청·직접 확인한 범위와 미확인:
- 구현·검증·미구현·실패·보장하지 못하는 범위:

## 기능별 예시와 실제 코드

핵심 기능마다 입력 한 건으로 설명하고 기술 용어는 쉬운 뜻을 붙인다. 소스 전체를 붙이지 않는다.

### [기능·요구 ID]

1. 사용자·시작 화면/명령·초기 상태와 입력 한 건:
2. 진입점→검사→계산→저장/결과의 실제 파일·함수 경로:
3. 선택 이유·다른 방법과 비교한 손실:
4. 적용 데이터·조건과 결과의 관계, 저장·조회·내보내기의 일치:
5. 입력 오류·계산 실패·중단·재시작 때 남는 상태와 사용자 표시:
6. 제3자가 실행할 파일·명령·확인할 상태와 실제 근거:
7. 사용자 확인/AI 검증/미확인의 범위:

## 책임과 상태

계획의 책임표를 연결해 실제 코드와 다시 대조한다. 기존 표가 없다면 아래 구분을 현재 확인 범위만큼 적고 계획에 연결한다.

- 규칙별 직접 검사 / 다른 계층 위임 / 미구현, 담당 코드/계층·보장 범위·재현 근거:
- 진행 중 작업 / 임시 결과 / 최종 결과 각각의 담당 위치·확정 시점·실패 결과·복구:
- 가장 취약한 지점·관찰 근거·보장하지 못하는 범위:
- 검사기가 생성기의 선택 순서/알고리즘과 달라도 유효한 결과를 수용하는 근거·전체 기간/공유 자원의 독립 검사:

Worker·큐·별도 프로세스가 없으면 없다고 설명한다. 요구에 없는 구조를 문서를 채우려고 구현하지 않는다.

## 품질·비용과 변경 영향

- 계획의 같은 입력/조건 기준 방법·현재 방법 비교와 규칙 준수 근거:
- 채택한 품질 지표·실제 값·측정 비용·개선/손실·미실행:
- 규모·조건 변경 결과·병목·추가 확인이 필요한 범위:
- 실제 실행·검사 명령/작업 디렉터리 또는 지정 실행 문서 경로:
- 설명 뒤 코드·자료·조건 변경의 영향과 사용자 재확인:

계획을 구현 사실로 복사하거나 설명 제공을 사용자 이해 완료로 기록하지 않는다. 어려운 부분을 재설명할 추천 요청과 다음 단계 요청을 알려주고 기다린다.
