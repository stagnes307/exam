# 시험 개발 하네스

사용자가 읽는 문서와 AI가 개발에 쓰는 문서를 나눈 시험용 지침·프롬프트·양식이다.

**처음 준비는 [START](START.md), 요청 복사는 [PROMPTS](PROMPTS.md), 전체 순서는 [QUICKSTART](QUICKSTART.md).**

## 내가 읽고 입력할 곳

| 실제 프로젝트 문서 | 용도 |
| --- | --- |
| **PROGRESS.md** | 짧은 현재 상태 + 전체 문제·자료·구조·핵심 알고리즘을 충분히 설명한 본문 + 직접 확인·보고 입력 |
| **PLAN.md의 질문 입력란** | 담당자에게 받은 답변을 직접 입력하고 저장 |
| **하네스의 PROMPTS.md** | 현재 단계의 짧은 기본 블록 하나를 복사 |

PROGRESS에는 담당자에게 보낼 질문과 PLAN의 답변 입력 위치를 안내한다. 답변 원문은 PLAN에만 남긴다. **초기 답변을 저장한 뒤에는 PROMPTS 2번**을 보낸다. 2번 프롬프트는 목적·우선순위 빈칸 없이 그대로 복사한다. AI가 원문·담당자 답변·기존 의견을 읽고 계획을 제안하며, 사용자가 결정할 사항만 쉬운 선택지로 설명한다.

추가 질문은 계획·구현 중에도 가능하다. AI가 답변을 구체적인 사례와 예상 결과로 대조하고, 결과가 달라지는 모호함이 남을 때만 질문을 이어간다. 사용자는 새 답변도 PLAN에 적고 기존 [답변 반영](PROMPTS.md#보조-담당자-답변-반영) 요청을 보낸다. AI는 현재 승인된 작업에 반영하고 영향받은 검사를 갱신한다. 원문과 충돌하는 답변은 정정 권한·적용 범위를 확인한다.

PRD·PLAN 전체·Phase별 개발 기록은 AI의 작업 문서다. 사용자는 PROGRESS 상단에서 지금 할 일을 확인하고 본문에서 프로젝트 전체를 이해한다. 목적·범위·자료 관계·출력의 뜻, 전체 구조와 각 핵심 알고리즘의 상태/동작·선택/결합 이유·복잡도/손실, 실패 후 상태와 검증 한계를 충분히 설명한다. 기술 문서 전체를 읽거나 기술적 목적을 다시 쓰거나 AI 검증을 직접 수행했다고 말할 필요는 없다.

## 개발 문서와 기록 위치

| 실제 프로젝트 문서 | AI가 관리할 내용 |
| --- | --- |
| PRD.md | 전체 요구·제외 범위·관찰 가능한 완료 기준·원문/질문 근거 |
| PLAN.md | 공통 질문/답변 원문·AI 검토, 전체 Phase 순서·의존 관계·상태·통합 검증 담당 |
| plans/의 Phase 파일 | 해당 Phase의 작업표·구현 위치·상세 증거·책임/실패 상태·변경 기록·반영한 사용자 보고 원문 |

**1 문제 파악 → 2 PRD·계획 확인 → 3 Phase 구현·AI 검증 → 필요한 경우 4 사용자 직접 확인 → 5 구현 설명 확인 → 6 제출 점검**

1단계에는 PROGRESS와 질문 입력용 PLAN만 필요한 만큼 작성한다. 질문이 없거나 일부 답변만 있어도 확정된 범위는 2단계에서 계획할 수 있다. 3번은 Phase마다 반복하며 한 Phase 안의 여러 기능·수정·재검증은 이어간다. AI가 허용된 CLI/API·자동 회귀 검사를 수행하고, 이미 통과한 CLI 명령을 사용자가 반복할 필요는 없다. UI 조작은 사용자가 플랫폼 Browser에서 직접 확인해 4번으로 전달한다. 다른 필수 사람 확인이나 별도 체험에도 4번을 쓴다. Phase 수나 P1~P4의 구성을 고정하지 않는다.

필수 검사마다 수행 주체·담당 Phase·시점·완료 기준을 계획한다. 통합 검사와 6번 제출본 확인에서도 CLI/API 검증과 사람의 화면 확인을 구분한다. PROGRESS에는 실제 검사 범위와 남은 필수 검사만 짧게 요약하며, AI가 하지 못한 검사를 통과로 바꾸지 않는다.

사용자는 직접 확인 결과를 PROGRESS에 적는다. AI는 반영한 원문을 기존 담당 Phase 한 곳에 안전하게 보관하고 현재 결론·미확인·원문 링크를 남긴다. Phase가 아직 없으면 PLAN을 사용한다. 보고 ID·판본 근거·링크는 AI가 관리하며 사용자는 별도 기술 항목을 입력하지 않는다. 실제 주체·판본·범위만 확인으로 기록하고 변경 영향이 있는 근거는 재확인 필요로 남긴다. 담당자 답변 원문은 계속 PLAN의 질문 ID에서 참조한다.

PROGRESS는 현재 설명을 갱신하고 과거 Phase 노트·명령·보고 이력은 누적하지 않는다. **짧게 할 것은 상단 상태와 반복 이력이며, 본문을 빈약하게 만들지 않는다.** 여러 알고리즘이면 핵심 풀이별 추적 예시와 앞뒤로 넘기는 상태·보장까지 설명한다. 목차로 필요한 부분을 찾을 수 있게 하고 바뀐 부분만 고친다. 판단·보장이 달라진 근거는 기존 Phase 이력에 남긴다. 퀴즈나 이해 완료 선언을 필수 절차로 만들지 않는다.

기존/지정 문서를 우선 재사용하고 없는 역할만 만든다. 테스트·구현 설명 양식은 별도 사용자 문서를 반드시 만들라는 뜻이 아니다. 지정 실행·협업·제출 문서는 실제 수행 근거로 채우고 PROGRESS나 계획으로 대체하지 않는다.

실제 과제 수행 중 PROMPTS의 기본 문구는 보존한다. 기본은 짧은 블록 하나이며, 예외가 있을 때만 같은 절에 적용 Phase/판본과 차이를 보충한다. PROGRESS는 정확한 절 제목·링크를 안내하고 프롬프트 전문을 다시 만들지 않는다. 과제별 보충은 제공 환경 안의 하네스 사본에만 기록한다.

## 유지할 확인 기준

- 생성기와 독립적인 기대값·최종 제약 검사, 다른 유효 결과 수용, 고의 오류 검출을 확인한다.
- 정상 A → 오류 B 거절 → 변경 C 적용 → 재계산·저장·조회·내보내기의 판본/조건/내용과 중단·재시작 상태를 연결한다.
- 단일 건·하루와 전체 기간·공유 자원 검증을 구분한다. 규칙 준수와 품질·실행 비용을 나누고 같은 입력의 기준 방법과 비교한다.
- 직접 검사/다른 계층 위임/미구현과 진행 중/임시/최종 상태의 책임·확정·실패 결과를 실제 코드로 기록한다.
- AI 검증·사용자 직접 확인·설명 제공·사용자 이해·실제 제출은 다른 상태다. 미실행과 남은 문제를 공개한다.

실제 시험의 요구·양식·허용 도구가 우선이다. 원문·원본 자료·기존 사용자 변경을 보존하고 변경 검사는 복사본으로 한다.

배포 저장소는 [stagnes307/exam](https://github.com/stagnes307/exam)이다. 사용자가 시험 전에 공개 상태로 준비한다. 설치 명령과 폴더 구조는 START에서 관리한다.

이 개발 저장소의 하네스 원본은 `exam-kit/`이다. 시험 프로젝트에 배포 저장소를 가져오면 START의 기본 이름인 `exam/`을 사용한다.
