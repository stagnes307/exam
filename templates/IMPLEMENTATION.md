# 프로젝트 전체와 핵심 풀이를 설명하는 AI 지침

`PROGRESS.md`는 상단의 빠른 상태 확인과 본문의 충분한 프로젝트 해설을 함께 제공한다. 본문은 짧은 요약문이나 단일 사례로 제한하지 않는다. 현재 설명을 갱신한다는 뜻은 서로 다른 알고리즘·자료·기능을 하나로 뭉개라는 뜻이 아니다. [PROGRESS 양식](../PROGRESS.template.md)의 실제 필요한 절을 채우고, 5단계에서 최신 코드·요구·근거와 대조한다. 전체 구현/사용자 테스트 완료를 설명의 전제로 삼지 않는다.

## 처음 읽는 사용자가 전체를 볼 수 있게

먼저 무엇을 만드는지, 누가 무엇을 입력해 어떤 결과를 얻는지, 필수 조건·목표 우선순위·기능/제외 범위를 설명한다. 자료별 역할·연결 키·단위·대상 범위와 출력 값의 뜻을 실제 값으로 보여 준다. 구현 뒤에도 이 기본 맥락을 없애거나 PRD 링크만으로 대체하지 않는다.

전체 입력→하위 문제/구성 요소→결합→최종 출력의 지도를 표나 간단한 흐름도로 만든다. 단순 파일명 목록 대신 각 부분의 입력·책임·결과·다음 부분이 믿을 수 있는 조건을 설명한다. 여러 알고리즘의 분해와 개발 Phase 순서는 구별한다. 없는 UI·DB·역할을 알고리즘 과제에 가정하지 않는다.

## 핵심 풀이마다 원리와 동작을 설명

[문제풀이 지침](../PROBLEM_SOLVING.md), PRD·Phase와 실제 구현을 대조한다. 서로 다른 상태·선택 원리·정당성을 가진 핵심 부분은 각각 설명하고, 공통 목표/제약·입력 정의·실패 상태는 한 번 설명해 연결한다. 단순 함수마다 형식적인 장문을 만들지 않는다.

- 상태와 자료구조의 한 칸/원소가 무엇을 뜻하며 왜 그 정보를 기억하는지 설명한다. DP·우선순위 큐·가지치기 같은 이름만 제시하지 않는다.
- 작은 입력으로 초기 상태·후보·선택/전이·갱신·종료·답 복원을 따라간다. 중요한 거절·되돌림·가지치기·최선해 보존이 있으면 그 지점의 전후 값과 이유를 보인다. 설명용 손계산과 실제 실행/측정은 구분한다.
- 어떤 전제에서 왜 맞는지, 선택/제거가 안전한 이유 또는 보장하지 못하는 부분을 설명한다. 증명 없이 '최적'이라고 쓰지 않는다. 필요한 수식/기호는 뜻·예시를 붙여 설명한다.
- 현실적인 대안이 왜 부적절하거나 더 비싼지, 선택한 방법의 품질/성능 손실이 무엇인지 작은 대비 사례와 실제 근거로 설명한다.
- 실제 최대 입력에서 상태 수·전이 수·반복 호출·자료구조/복원 비용이 어떻게 커지는지 보여 준다. 기호 하나로 끝내거나 작은 실측으로 전체 성능을 보장하지 않는다.

### 여러 풀이가 이어지는 경계를 설명

앞 부분이 결정/보류하는 것, 다음 부분에 넘기는 대안·자원 사용·이력과 버리는 정보를 밝힌다. 앞의 국소 최적이 뒤의 가능성/전체 목표를 망칠 수 있는지, 나누어도 되는 근거와 필요한 되돌림 책임을 설명한다. 내부 가능성 판정이 정확한지 또는 휴리스틱인지도 외부 탐색의 보장과 연결한다.

전처리·알고리즘·결과 복원이 각각 맞아도 ID/단위/순서/공유 상태를 넘기며 오류가 날 수 있다. 전체 예시에서 그 연결을 보이고 원시 입력부터 최종 출력까지의 독립 대조 근거를 남긴다. 하나의 예시로 중요한 차이가 드러나지 않으면 해당 하위 문제/경계의 작은 추적을 추가한다.

## 실제 구현·상태·검증으로 연결

대표 입력의 전체 흐름을 실제 모듈/함수의 역할로 연결하고 직접 검사·다른 계층 위임·미구현을 구분한다. 저장 기능이 있으면 편집본·적용 자료·작업 후보·최선 유효해·확정 결과처럼 실제 상태의 뜻부터 설명한다. 오류·입력 변경·중단·재시작 때 무엇이 유지/무효화되는지와 복구 책임을 보여 준다.

검증은 실제 주체·판본·조건·대표 결과를 밝히고 독립 기대값과 앱의 자체 검사를 구분한다. 작은 사례·큰 입력·경계/반례·하위 모듈·전체 연결 검사가 각각 무엇을 입증하는지 설명한다. UI가 있으면 CLI/API·화면 반응·파일 생성/내용 확인의 경계를 구분한다. 현재 실패·미실행은 영향·해소 조건·후속 담당까지 본문에 남긴다.

정확해·허용된 근사/휴리스틱·유효해 미발견·불가능 입증을 실제 근거에 맞춰 구분한다. 제한 탐색에서 좋은 결과를 얻었다고 전체 최적성을 주장하지 않는다. 실제 구현에 없는 상태·병렬화·성능 개선·보장은 만들지 않는다.

## 갱신과 충분성 점검

상단만 짧게 유지하고 본문은 필요한 만큼 설명한다. 목차·표·단계별 예시를 써서 다시 찾기 쉽게 한다. 과거 Phase 설명·처리한 보고·명령/해시/실행 로그는 누적하지 않으며 상세 근거와 원문은 담당 Phase/PLAN에서 연결한다. 현재의 자료 의미·기능 범위·모형·핵심 이유는 링크 뒤로 숨기지 않는다.

코드·자료·조건 변경에 영향받은 설명과 검증 범위만 갱신한다. 판단·보장이 바뀐 이유와 이전 근거는 Phase 이력에 보존하되 매번 설명 전문을 복제하지 않는다. 보고만 반영할 때는 관련 상태/근거만 바꾸고 전체 해설을 다시 쓰지 않는다.

AI는 작성 뒤 본문만 읽어 다음 연결이 가능한지 자체 점검한다: **전체 목적/범위 → 자료와 정답 조건 → 하위 문제/해법 선택 → 상태와 실행 과정 → 결합·답 복원 → 실패 복구·검증 한계**. 중간이 알고리즘 이름이나 링크 하나로 끊기면 보완한다. 이 점검을 사용자 퀴즈로 보내지 않는다. 설명 내용의 누락 점검은 실제 인간 이해도나 점수 검증이 아니다.

사용자가 더 설명을 원하면 해당 부분을 충분히 보완한다. 기술 문서 전체 독해·같은 CLI 반복을 설명의 조건으로 삼지 않는다. 설명 제공·사용자 이해·직접 검사·제출은 별개이며 실제 보고 없이 완료를 기록하지 않는다. 후속 서술형 답안을 대신 작성·첨삭하지 않는다.
