# Phase 개발 계획과 실행 근거

AI 개발용 상세 양식이다. 2단계에서 실제 정한 Phase만 `plans/P1.md` 같은 파일로 작성한다. 현재 필요한 절만 사용하고 미래 기능·빈 실행 표를 미리 늘리지 않는다. 사용자가 읽을 설명·직접 테스트·인지 대비 정보는 `PROGRESS.md`에 작성한다.

## 범위와 선행 조건

| Phase ID·상태 | 관련 요구·PRD/PLAN 링크 | 선행 Phase/조건 | 실행 가능한 결과·완료 기준 |
| --- | --- | --- | --- |

- 승인된 범위·사용자 요청 근거:
- `PLAN.md`의 관련 질문/변경 ID·확정 해석 링크·미확정 의존 범위:
- 이번에 포함하지 않는 후속 통합 범위:

담당자 답변 원문은 `PLAN.md`만 참조한다. 사용자에게 PRD·기술 계획 전체를 읽었다고 말하게 하지 않고 `PROGRESS.md`의 범위/선택 사항을 확인한 실제 요청을 근거로 삼는다.

## 검증 계획과 실제 결과

기대값은 앱 출력 전에 원문·손계산 등 별도 근거로 정한다. CLI/API·단위·입력 검증·회귀 검사는 AI가 실행하고 수정·재검증한다. API는 실제 요청으로 검사한다. UI 조작은 사용자가 플랫폼 Browser에서 수동 확인한다. 이미 통과한 CLI 명령의 사용자 반복 실행을 Phase 종료 조건으로 삼지 않는다. 미실행·실패·재확인 필요는 원인·범위·영향과 함께 그대로 기록한다.

| 검증 ID·요구 ID·검사 계층 | 계획 수행 주체·담당 Phase·실행 시점/선행 조건 | 초기 상태·입력/조작 | 기대·원문/독립 계산 근거 | 명령·작업 디렉터리·판본 | 실제·종료 코드·확인 주체·미확인 이유 |
| --- | --- | --- | --- | --- | --- |
| | | | | | 미실행 |

검사 전 각 필수 검사의 수행 주체·시점·선행 조건·완료 기준과 근거 위치를 계획한다. 모듈/CLI/API·UI 기능·전체 연결 흐름을 구분하고, 단위검사 통과만으로 UI나 전체 흐름 통과를 기록하지 않는다. 없는 후속 기능의 통합 검증은 `PLAN.md`의 담당 Phase와 실행 조건으로 연결한다. 현재 Phase 필수 검사에 실패·미실행이 남으면 해당 검증은 미완료이며, 현재 완료 기준 충족과 후속 통합 미완료는 별도로 표시한다. 매 Phase에 전체 미래 기능 검사를 강제하지 않는다.

- 공유 파서/계산/시간 함수가 함께 틀릴 수 있는 사례와 독립 대조:
- 생성기 재실행과의 일치 대신 입력·최종 출력 제약을 직접 검사한 근거:
- 다른 유효 결과 수용·정상 결과 복사본의 고의 오류 거절:
- 단일 건/하루와 전체 기간·공유 자원 검사 구분:
- 미배정/거절 사유·누적 제약의 기준 시점과 우선순위 대조:
- 실패 원인·수정 위치·같은 사례/기존 정상 흐름의 재검증:

**입력 계약과 보존:** PRD에서 정한 독립 근거로 허용/거절 판정을 먼저 정하고, 유효한 동치 표현·경계값·서로 다른 자료형/구조의 위반 입력을 실제 진입점에서 대조한다. 임의 예외로 새지 않고 정해진 오류 계약으로 끝나며 입력과 이전 성공 결과가 보존되는지 확인한다. 파일 입출력은 다른 경로 표기가 같은 실제 대상을 가리키는 경우도 검사한다. 원문이 변경을 요구한 기능 외에는 보존할 원본을 출력으로 덮어쓰지 않는다.

환경 문제는 본인 앱·본인 프로세스 안에서 해결한다. 플랫폼 자체 장애로 실행하지 못한 검사는 미확인으로 남긴다.

원본 자료와 정상 결과는 보존하고 변경/고의 오류 검사는 복사본으로 한다. 영구 데이터셋은 원문이 요구한 준비 자료와 실제 선택·재현에 필요한 묶음으로 제한하고 목적을 기록한다. 세부 경계값·조합별 테스트 복사본은 임시 디렉터리에서 생성·정리한다. 원문이 요구한 정상/오류 준비 자료는 실제 파일로 보존하며 임시 테스트만으로 대체하지 않는다. 이미 검증 명령·문서에서 사용하는 자료는 영향 확인 없이 삭제하거나 합치지 않는다. 기술 결과를 AI 확인·사용자 직접 확인·설명 제공·사용자 이해·실제 제출과 구분한다.

### 데이터 적용부터 출력까지의 일관성

실제 데이터 변경·생성·저장 요구가 있을 때 적용한다. 정상 A·오류 B·변경 C는 복사본으로 준비하고 자료 종류별 변경도 확인한다. 없는 기능은 후속 통합 검증으로 연결하고 해당 없는 조건은 이유를 적는다.

| 시나리오 | 확인할 관계·상태 | 입력/조건/결과 식별 근거·검증 ID·실제/미확인 |
| --- | --- | --- |
| 정상 A 적용·생성 | 선택/검증/적용 데이터와 생성 조건·결과가 대응 | |
| 오류 B 적용 거절 | 오류 원인 표시, 기존 A·확정 결과 유지 | |
| 정상 C 적용 | 과거 결과가 C의 최신 결과처럼 표시/내보내기되지 않음 | |
| C 재계산·저장·조회·내보내기 | 검사한 결과와 저장/조회/출력의 데이터 판본·조건·내용 일치 | |
| 처리 중단·검증 실패·재시작 | 부분 결과를 완료로 공개하지 않음, 기존 결과·복구 상태는 요구대로 유지 | |

식별 근거는 실제 ID·조건·해시·레코드 등으로 남기며 특정 버전 관리 구현을 강제하지 않는다. 건수나 출력 변화 여부만으로 재계산·내용 일치를 증명하지 않는다. 여러 Phase에 걸친 시나리오는 `PLAN.md`의 담당 Phase에서 최종 증거를 관리한다.

같은 입력으로 비교한다. 지표의 정의·방향·선택 이유는 PRD를 연결하고 실행 시간 등 측정한 비용을 적는다. 규모 확대와 핵심 조건 변경도 확인한다. 개선되지 않은 지표·손실·미실행을 공개하고 임의의 개선률을 만들지 않는다.

### 알고리즘 정확성·요구 수준 확인 — 해당 과제만

알고리즘을 구현·수정하는 Phase에서는 [문제풀이 지침](../PROBLEM_SOLVING.md)을 다시 읽고 PRD의 정의·해법에 따라 구현·독립 검증·해당하는 품질 개선을 수행한다. 기존 작업/검증 표와 위 품질 비교 표에 아래 근거를 연결한다. 다른 Phase나 해당 없는 과제에 모든 방법을 반복해서 강제하지 않는다.

- 원문 문제·입력 해석·목적함수·제약·우선순위·요구 정확성과 실제 코드의 상태/변수/조건/전이 대응, 탐색용 후보 제한·고정한 결정의 근거와 영향:
- 선택한 해법의 전제·정당화·시간/공간 복잡도와 실제 구현의 일치:
- 하위 문제의 입출력·보장·넘길 상태/대안과 결합 근거, 실제 연결 코드·ID/단위/순서·정답 복원·원시 입력부터 최종 출력까지의 독립 대조:
- 채택한 상태/선택/단조성/가지치기를 공격한 작은 반례와 결론, 상태 수×전이/자료구조 비용·내부 호출 횟수·메모리의 실제 최대치와 측정:
- 원문·원시 입력에서 해석을 대조한 작은 기대 사례, 독립 작은 참조·정상/경계/반례/무작위 검사, 정확해 또는 허용된 근사/휴리스틱 수준에 맞는 판정과 품질 격차:
- 발견한 오류의 최소 재현·원인·수정·회귀 결과·같은 원인의 적용 범위와 남은 위험:
- 필요한 최적화의 기준 방법·개선 후보별 유효성/품질/비용·보존한 최선 유효해·탐색 중단 이유, 확률적이면 재현 조건과 변동:
- 허용 규모·극단 조건에서 실제 진입점의 시간/공간 비용·품질과 남은 미검증 범위:
- 유효해 발견/미발견·중단 이유/불가능 입증의 근거와 적용 범위, 실제 증거가 뒷받침하는 정확성/최적성 수준·미입증·한계, PROGRESS 설명 위치:

담당자 답변 해석이 달라지면 PLAN의 질문 ID로 변경된 정의·작업·검사를 연결하고 기존 근거를 보존한다. 지침을 읽었다는 표시나 검증 계획만으로 실행 완료를 기록하지 않는다.

## 코드 책임과 실패 상태

구현할 때부터 실제 코드로 기록한다. 기능별 입력 예시·파일/함수·선택 이유·한계와 재현 근거를 아래 표에 연결한다. PROGRESS 본문에는 전체 구조와 핵심 풀이별 상태·전이·작은 추적·선택/결합 이유를 충분히 설명하고 이곳의 상세 증거를 연결한다.

| 규칙·요구 ID | 직접 검사 / 다른 계층 위임 / 미구현 | 담당 코드/계층·보장 범위 | 재현 명령·증거·한계 |
| --- | --- | --- | --- |
| | | | |

| 실제 상태 | 담당 컴포넌트·보관 위치 | 확정/갱신 시점 | 실패·중단 후 남는 것·복구·확인 근거 |
| --- | --- | --- | --- |
| | | | |

진행 중 작업·임시 결과·최종 결과를 실제로 존재하는 만큼 구분한다. 없는 상태·Worker·큐·별도 프로세스는 가정하지 않는다.

## 변경·재확인과 Phase 종료

| 판본·변경 ID | 변경 내용·이유/근거 | 영향받는 요구·Phase·검증 | 수정/재검증·재확인 필요 |
| --- | --- | --- | --- |
| | | | |

- 사용자 직접 확인 대상·규정/업무상 이유 / 허용된 AI 검사의 실행 불가 원인·본인 앱의 해결 시도·남은 최소 범위 / 아래 보관 원문의 고정 ID·주체·판본·범위/현재 유효성:
- 필수 제출물·지정 문서에 반영한 근거·실제 경로:
- 현재 구현/AI 검증/미구현/실패/미확인·남은 통합 검증·다음 작업:
- 중간 종료 시 진행 중/부분/확정 결과·미저장 변경·현재 제출 준비 상태:

현재 상태를 먼저 갱신하고 과거 검증은 판본과 함께 짧은 이력으로 남긴다. 계획·프롬프트·사용자 보고를 반복 복사하지 않는다. 코드·자료·조건 변경에 영향받은 검증과 사용자 확인은 재확인 필요로 표시한다. 요구·완료 기준·다른 Phase의 범위/순서가 바뀌면 PRD·PLAN·관련 Phase를 함께 갱신한다. 결과·인지 대비 설명·미확인은 PROGRESS에 반영한다.

PROGRESS의 현재 설명에서 판단·보장·실패 상태가 달라진 이유와 이전 근거는 이 이력에 남긴다. 매 보고마다 이전 쉬운 설명 전문을 복제하지 않는다. 현재 설명은 전체 구현 하나로 유지하고 영향받은 부분만 갱신한다.

현재 Phase의 필수 검사와 필요한 수동 확인이 충족되면 요약·한계와 다음 Phase의 3번 요청을 안내한다. UI 조작·업무 판단 등 사람의 확인이 남으면 최소 절차와 결과 전달용 4번을 안내한다. 미완료 항목에 의존하지 않는 Phase는 독립성을 설명하고 사용자 요청 뒤 진행할 수 있다. 기존 미완료와 후속 통합 상태를 유지하며 실제 대상 Phase와 할 일을 설명한 뒤 다음 요청을 기다린다.

## 사용자 보고 원문 — 실제 보고가 있을 때만

[사용자 확인 지침](USER_TEST.md)에 따라 PROGRESS에서 반영한 보고를 보관한다. AI가 프로젝트 전체에서 고유한 `### UT-001` 같은 고정 제목/앵커를 만들고 **실제 원문을 변경 없이** 둔다. 주체·판본/조건·적용 범위·현재 유효/재확인 필요와 AI 해석은 원문 밖에 쓴다. 사용자에게 ID·해시를 입력하게 하지 않는다.

한 보고가 여러 Phase에 걸쳐도 담당 한 곳에 원문을 보관하고 다른 곳은 연결한다. 정정·다른 판본의 새 실행은 새 ID로 추가하며 이전 보고를 고치지 않는다. 원문 동일성과 PROGRESS의 현재 입력을 재확인하기 전 입력을 비우지 않는다. 보관됐어도 필수 실패·미확인은 현재 상태와 PROGRESS에 계속 남긴다. 미처리 보고는 PROGRESS에서, 초기 PLAN에 이미 보관된 보고는 그 원본에서 읽는다.
